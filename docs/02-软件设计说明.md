# 软件设计说明

**产品名称**：dsh-request-doctor（请求急救员）
**版本**：0.11.0
**编制依据**：GB/T 8567-2006《计算机软件文档编制规范》6.2

---

## 1 引言

### 1.1 标识

本文档描述 dsh-request-doctor 0.10.0 的体系结构、模块划分、接口与关键算法。需求来源见《软件需求规格说明》。

### 1.2 系统概述

插件是 DSH 宿主进程内的一个 Cordis 插件，通过四类扩展点介入运行时行为，并在后台周期性校验插件生态的一致性。整体为单进程、事件驱动、无外部依赖。

### 1.3 文档概述

第 2 章给出体系结构，第 3 章逐模块说明职责与接口，第 4 章给出关键算法与数据结构，第 5 章说明错误处理与恢复，第 6 章说明设计权衡。

### 2.3 并发模型

- 单线程事件循环。
- 版本扫描以布尔标志互斥，进行中的扫描不被第二次扫描打断。
- 事件驱动的扫描请求合并：同一时刻最多一个待执行扫描。
- 定时器为 `unref`，不阻止进程退出。

## 3 模块设计

### 3.1 组合根 `index.js`

导出 `name` 与 `apply(ctx, rawConfig)`。

`apply` 的执行顺序：

1. 解析配置；`autoRepair` 为假则记录日志并直接返回。
2. 建立 `AbortController`（插件生命周期）、定时器集合、定时器助手。
3. 建立诊断、运行时探针、重试账本、版本修复器、修复监听器。
4. 注册三类事件监听：
   - `agent/request-error`（局部）
   - `tools/execute`（局部）
   - `connection/request`（全局：载体在兄弟上下文）
5. 注册扫描调度（`app-boot/config-reload`、`plugin-manager/changed`，均为全局事件）。
6. 注入 `commands` 注册 `/doctor` 命令；注入 `webServer` 注册界面用的三条路由。
7. 注册释放钩子：中止生命周期、停止扫描、清空定时器、刷新诊断。

### 3.2 `lib/model-repair.js`

| 接口 | 说明 |
| --- | --- |
| `createModelRepair(input)` | 返回 `{ handle }` |
| `handle(payload, next)` | 处理一次请求失败 |

`handle` 流程：

```
await next()                      // 先让下游决定
  下游要求重试 → 直接返回（尊重 provider 策略）
  信号已中止 → 返回下游结果
  分类失败 → 非客户端原因或 skip 策略 → 返回下游结果
  strategy = version-repair → 触发版本修复；未修复则放弃
  strategy = compact → 压缩上下文 + 裁剪工具结果
  scheduleRetry：
    取预算条目，计数 +1
    超过上限 → 首次超限记录 give-up，返回下游结果
    计算退避 → 记录 llm/retry → 等待（可中断）
    记录 llm/retry-started → 返回 { kind: 'retry' }
```

### 3.3 `lib/repair-listeners.js`

| 接口 | 说明 |
| --- | --- |
| `createRepairListeners(input)` | 返回三个监听函数 |

- `onToolExecute`：`attemptDispatch` 判定一次执行是否需要重放；需要则退避后重来，直到预算耗尽或错误不可重放。
- `onConnectionRequest`：响应头未发出且为瞬时传输错误时写 503；否则原样抛出。

### 3.4 `lib/version-repair.js` 与 `lib/plugin-discovery.js`

| 接口 | 说明 |
| --- | --- |
| `createVersionRepair(input)` | 返回 `{ run, isBusy }` |
| `run(reason, manager?, attempt?)` | 执行一轮版本修复 |
| `collectMismatched(bundles, facts, plugins, probe)` | 收集所有需要处理的插件（在 `plugin-discovery`） |

内部阶段：

1. **发现** `collectMismatched`：合并四类候选并按包名去重。
   - `deferredCandidates`：有 staging 标记且未建环境的包
   - `refusedCandidates`：Loader 已拒绝的包（含其算出的未满足集合）
   - `installedCandidates`：清单里已存在的插件中，声明未满足或环境缺件者
   - `scannedCandidates`：直接扫 profile 的 `node_modules`，补上 `listPlugins()` 看不到的插件
     （加载失败的不在 Loader 树里，恰恰最需要处理；`link:` 安装的是符号链接，也要算）
2. **审计** `auditAll` → `auditOne`：逐包调用 `auditInstalledPlugin`，异常降级为 `review`。
3. **仲裁** `providerRoster` + `describeContention`：只生成报告条目。
4. **适配** `adapt`：构建兼容环境、对齐 manifest、**核对环境**。
5. **重载**：对本次适配成功的包调用 `setBundleEnabled(name, true)`；检测到 HMR 嵌套错误则退避重试。

适配之后的核对是必要的一步。建好环境不等于能用：垫片少写一个导出，插件在加载那一刻
就会崩，而修复流程还以为成功了。`verifyEnvironment` 逐条确认插件要的每个符号环境是否真能
给出来，通不过就记为未修复而不是谎报成功。

### 3.4a `lib/env-verify.js`

| 接口 | 说明 |
| --- | --- |
| `verifyEnvironment({pluginDir, imports})` | 核对整个环境，返回 `{ok, problems, unverified}` |
| `verifyPackage(pluginDir, name, symbols)` | 核对单个包，返回 `provided` / `missing` / `unverifiable` |

三种结论的区分很重要：

- `missing`：目标读得到，但确实没有这个符号。这是真问题。
- `unverifiable`：目标读不到（运行时包常装在归档里）。不算失败，只是这次核对不了。
- `provided`：能找到。

`default` 需要单独判断——`export *` 从不转发默认导出，目标有 `default` 不等于插件拿得到，
必须由垫片自己写出来。

### 3.4b `lib/package-fetch.js`

| 接口 | 说明 |
| --- | --- |
| `fetchPackage(name, version, destDir)` | 从注册表取指定版本，解压到目标目录，返回 `{ok, error?}` |

兼容模式的落地靠这个模块。插件当初是对着某个版本写的，那个版本的代码还在仓库里，取下来装上就行——跑的是它认识的那份实现，不是转发到今天实现的替身。

实现是纯 Node：`fetch` 拿 tarball，`zlib.gunzipSync` 解压，自己解析 tar 头。不引第三方依赖，因为插件要在没有额外包的 profile 里运行。

解压时做了目录穿越防护：每个解出来的路径必须仍在目标目录内。

### 3.4c 旧版本的获取流程

1. `adapt` 先做一次 `dryRun` 探测：只问「能不能建」，一个字节不写。
2. 探测返回 `needs-old-version` 时进入版本搜索：先试插件声明的版本，再试声明范围内的其余版本，最后才试范围外的。第一个凑齐符号的版本胜出。取回的缓存在 `<profile>/.request-doctor-cache/`。
3. 取回了再建一次环境：符号在旧版本里确实有，就把整份旧实现放进去；旧版本也没有，如实报缺。
4. 旧版本自己的运行时依赖（`@deepseek-ai/*`，版本按声明钉死）也一起解析、一起装。只装它一个的话，它加载时 import 的兄弟包要么找不到，要么拿到新版本，两种都不是插件当初的环境。闭包最多 16 个包。

`dryRun` 不是可选项。探测调用如果落盘，在 profile 目录上执行时会把里面的真实包覆盖成垫片——一次只该读的检查，改掉了运行时依赖。

### 3.5 `lib/compat-env.js`

| 接口 | 说明 |
| --- | --- |
| `installCompatEnvironment(input)` | 构建环境，返回 `installed` / `unchanged` / `refused` / `failed` |
| `alignManifest(input)` | 对齐 DSH 依赖声明，返回 `aligned` / `already` / `skipped` / `failed` |
| `restoreManifest(dir)` | 还原原 manifest |

### 3.6 `lib/install-support.js`

| 接口 | 说明 |
| --- | --- |
| `prepareForInstall(input)` | 安装前预置，返回 `{prepared, packages, deferred, reason}` |
| `classifySpec(spec, profileDir)` | 判定本地目录或远程包 |
| `abandonPreparation(dir)` | 回滚预置 |
| `readStagedPreparation(dir)` | 读取 staging 标记 |
| `clearStagedPreparation(dir)` | 清除 staging 标记 |
| `preparationSurvived(dir)` | 判断预置是否仍在 |

`prepareForInstall` 分解为：`inspectCandidate`（校验）→ `resetPreviousAttempt`（清残留）→ 构建 → 分支：

- 仅因运行时包不可见而拒绝 → `deferEnvironment`：只对齐 manifest，交给后续扫描建环境
- 成功 → `finalizePreparation`：对齐 manifest 并写 staging 标记

### 3.7 领域模块

- `lib/semver.js`：`parseSemver`、`compareVersions`、`satisfies`、`classifyDistance`。`satisfies` 支持 `=`、`>`、`>=`、`<`、`<=`、`^`、`~`、`x` 通配、空格与 `||` 组合。
- `lib/classify.js`：失败分类采用**规则表** `CLASSIFICATION_RULES`，首条匹配即返回。顺序编码优先级：provider 侧拒绝先于通用传输判定。
- `lib/compat.js`：`collectDshImports`（解析具名导入）、`collectProviderIds`、`collectIdLiterals`（要求 `id` 与 `region` 成对）、`parseExportedNames`、`auditPluginCompatibility`。
- `lib/compat-repair.js`：`collectPackageFacts` 遍历模块图，`walkModuleGraph` 限 40 个文件；`auditInstalledPlugin` 产出 verdict 与 `importMap`。
- `lib/arbitrate.js`：给定静态声明、冲突集与运行时注册表，描述争用关系，不产生任何环境变更。

### 3.8 基础设施模块

- `lib/timers.js`：`createTimers(ctx, timers)` → `{ later }`。通过 `hmr.executing.exit()` 脱离激活事务，否则插件管理器报 "HMR transactions cannot be nested"。
- `lib/sleep.js`：`cancellableSleep(ms, signal)`，中断返回 `false`。
- `lib/stat-cache.js`：`createManifestReader()`（上限 512）、`createFactsReader(collect)`（上限 256）。键为文件签名，变更自失效。
- `lib/runtime-probe.js`：`createRuntimeProbe(input)`，提供 `runtimeFacts`、`runtimeDirOf`、`runtimeEntryOf`、`activeProviders`、`factsOf`、`get`。
- `lib/diagnostics.js`：`createDiagnostics(input)`，250 ms 合并写入，日志上限 30 条。
- `lib/retry-ledger.js`：`createRetryLedger(input)`，每 agent 上限 128 条链。

## 4 关键算法与数据结构

### 4.1 兼容环境构建

对插件导入的每个 `@deepseek-ai/*` 包：

1. 定位真实包目录；找不到则记入 `missing` 并拒绝。
2. 读取真实包入口，解析其导出名集合。
3. 若插件使用了真实包中不存在的符号 → 拒绝，报告该符号。
4. 否则在 `<插件>/node_modules/<包名>/` 写入：
   - `package.json`：`name` 为原包名，`version` 为目标旧版本，`type: module`，`exports` 指向 `index.js`
   - `index.js`：`export * from '<真实入口 file URL>'`；仅当真实入口有默认导出时追加 `export { default } from ...`
5. 写入仅在内容变化时发生。

Node 的向上查找使嵌套 `node_modules` 遮蔽 profile 中的同名包，从而实现"给插件一个它期望的旧环境"。

### 4.2 Manifest 对齐

改写 `peerDependencies` 中所有 `@deepseek-ai/*` 项，以及 `engines.dsh`，目标为环境实际服务的版本（无环境时用运行时版本）。写入前若备份不存在则先备份；写入采用写临时文件后 `rename`，因为 pnpm 以硬链接方式把 manifest 放入 `node_modules`，原地写入会污染存储。

### 4.3 审计判定

`auditPluginCompatibility` 产出 `verdict`：

| verdict | 条件 |
| --- | --- |
| `compatible` | 无未满足 peer；或距离 ∈ {satisfied, prerelease-delta, patch-delta} 且导入符号齐全 |
| `incompatible` | 存在缺失符号，或距离 ∈ {major-delta} |
| `review` | 距离 ∈ {minor-delta, unknown}，或无法读取源码 |

只有 `compatible` 会被自动适配。

### 4.4 退避计算

`computeDelay(config, attempt, failure)`：`initialDelayMs * 2^(attempt-1)`，上限 `maxDelayMs`，再乘以 `1 ± jitterRatio` 的随机因子。默认 400 ms、上限 20 s、抖动 25%。

### 4.5 主要数据结构

```js
// 重试预算条目
{ count: number, retryId: string }

// 运行时事实（每次扫描重建，缓存不在其中）
{ runtimeVersion, profileDir, packages, baseUrl }

// 审计行
{ name, version, runtimeVersion, requirements, deferred,
  verdict, reasons, missing, imports, importMap, providers, conflicts, contention }

// 兼容环境标记
// .request-doctor-compat.json
{ runtimeVersion, packages: string[] }

// 安装预置标记
// .request-doctor-staging
{ runtimeVersion, packages: string[], deferred?, requirements? }
```

## 5 错误处理与恢复

| 情形 | 处置 |
| --- | --- |
| 可选服务缺失 | `ctx.get(name)` 包裹 try/catch，缺失即降级，不中断 |
| 单个插件不可读 | 该插件审计降级为 `review`，其余继续 |
| 环境构建被拒绝 | 记录 `compat-refused`，不重试 |
| 环境构建失败 | 记录 `compat-failed`，下轮扫描重试 |
| HMR 事务嵌套 | 退避后重试，上限 `maxHmrRetries` |
| 诊断写入失败 | 吞掉异常，诊断不得影响修复 |
| 插件释放 | 中止生命周期信号、清空定时器、刷新诊断 |

## 6 设计权衡

1. **不绕过检查而给环境**：直接写版本豁免会让插件在错误假设下运行；给环境使其声明与实现一致，是唯一能同时满足用户诉求与正确性的做法。
2. **只适配审计通过者**：把"声明不匹配"与"能否真正运行"分开判定，避免把不兼容插件伪装成可用。
3. **规则表驱动分类**：相较于长 `if` 链，规则表让优先级与判定粒度显式可读，也便于单测逐条覆盖。
4. **缓存键用文件签名**：不引入文件监听，避免监听器自身成为资源负担与竞态源；签名失配即重算。
5. **扫描合并与退避**：健康 profile 的稳态开销趋近于零，异常时立即回到基础周期。
6. **路由冲突只报告**：插件归属用户，自动化不应替用户决定停用哪一个。

### 2.6 界面层

界面是一个独立的客户端模块 `client.js`，通过 `dsh.client` 声明，注册到插件面板的标签栏与设置里插件页的标签。它不持有业务逻辑：清单从 Host 路由读，安装请求交给 Host 执行。

客户端与 Host 之间有两条通道，实际只用后者：

| 通道 | 用法 | 结论 |
| --- | --- | --- |
| typert 远程服务 | `ctx.remote.pluginManager` | 动态加载的客户端模块拿不到该门面，实测恒为 undefined |
| 同源 HTTP 路由 | `fetch('/doctor/...')` | 可用；与插件管理器自身界面同一机制 |

Host 侧提供三条路由：

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| GET | `/doctor/incompatible` | 返回需要处理的插件：本插件审计结果 + 管理器拒装记录，去重 |
| POST | `/doctor/install` | 装一个包，复用 `/doctor install` 的实现 |
| GET | `/doctor/rescan` | 立即触发一轮审计 |

界面元素与数据流：面板读清单 → 每行一个「授权并安装」→ POST 安装路由 → Host 完成授权、重装、声明对齐 → 面板刷新清单。

### 2.7 失败分类与处置

分类的粒度按「修复动作」划分，不按报错原文划分：同一句话在不同上下文里可能要不同处理。

| 归类 | 处置策略 | 具体动作 |
| --- | --- | --- |
| `tls` | 放弃 | 证书问题重试不会变好 |
| `quota` / `policy` / `image` | 放弃 | 对方侧原因，不干预 |
| `local-blocked` | 放弃 | 权限、路径、磁盘、沙箱：缺的不是时机 |
| `auth` | 刷新凭据后重试 | 依次询问 `credentials` / `auth` / `accounts` 服务 |
| `model` | 刷新模型目录后重试 | 依次询问 `modelCatalog` / `models` / `providerRegistry` |
| `overflow` | 压缩后重试 | `compaction.compactIfNeeded` + `toolResultPruner.pruneSession` |
| `compaction-loop` / `history` | 修历史后重试 | 裁剪工具结果 + `sessionStore.flush` |
| `version-repair`（适配器缺失） | 修版本后重试 | 交给版本修复模块，未修成则不重试 |
| `local-env` / `stream` / `mcp` / `protocol` / `provider-error` / `timeout` / `empty` / `transport` | 退避重试 | 指数退避 + 抖动，受预算约束 |

### 2.8 三道防护

| 防护 | 机制 | 对应缺陷 |
| --- | --- | --- |
| 并发 | 同一 `turn:step:provider:kind` 同时只允许一个重试在飞，其余直接交还下游 | 并发控制 bug |
| 无进展 | 同一处连续两轮修复未见效即停手并记 `give-up` | 压缩自死循环、重试策略缺陷 |
| 循环 | 同名同参调用超过 `maxRepeatedToolCalls` 后不再重放 | 工具调用循环检测失效 |

### 2.9 预算分配

| 策略 | 额度 | 默认值 |
| --- | --- | --- |
| 普通重试 | `maxRetries` | 12 |
| 鉴权 | `maxAuthRetries` | 2 |
| 修历史 | `maxRetries` 的三分之一 | 4 |
| 工具重放 | `maxToolRetries` | 2 |
